1. PROJECT ELEVATOR PITCH & HIGH-LEVEL OVERVIEW
================================================================================

Q: What is PocketDay?
A: PocketDay is a modern, offline-first personal finance application built with 
   Flutter and Firebase. It helps users track income and expenses, set monthly 
   category budget limits, manage savings goals with dynamic progress tracking, 
   and track recurring subscriptions with automatic expense recording.

Q: What key problem does PocketDay solve?
A: 1. Fragmentation: Combines daily expense tracking, monthly budgets, target 
      savings, and recurring subscriptions into a unified dashboard.
   2. Poor Offline Support: Unlike web-dependent finance apps, PocketDay uses 
      Cloud Firestore's native offline persistence engine so users can log 
      transactions anywhere without network delays.
   3. Complex Setup: Offers instant Google OAuth sign-in and intuitive 
      Material 3 navigation without cumbersome setup steps.

2. TECH STACK & SYSTEM ARCHITECTURE
================================================================================

Q: What technology stack is used in PocketDay?
A: - Framework: Flutter (Dart 3.11+)
   - State Management: flutter_riverpod (StateNotifierProvider, Provider)
   - Authentication: Firebase Auth + Google Sign-In (OAuth 2.0)
   - Database: Cloud Firestore with Native Offline Disk Persistence
   - Design System: Material 3 (Google Fonts - Inter, AppColors palette)
   - Data Visualization: fl_chart (Interactive pie charts)
   - Micro-Animations: flutter_animate

Q: What architecture pattern does PocketDay follow?
A: PocketDay follows a Feature-First Clean Architecture:
   - UI Layer (lib/features/*/views & lib/core/widgets): Flutter widgets consuming providers.
   - State Management Layer (lib/features/*/providers): Riverpod StateNotifiers holding immutable states.
   - Repository Layer (lib/data/repositories): Abstraction layer handling Firestore API & stream calls.
   - Domain/Model Layer (lib/data/models): Immutable entities (UserModel, TransactionModel, BudgetModel, GoalModel, SubscriptionModel).

Q: Why Feature-First over Layer-First directory structure?
A: Feature-first groups files by business feature (auth, budget, dashboard, goals, 
   subscriptions, transactions). This makes the codebase scalable and modular, 
   allowing developers to modify a feature without hunting across separate layer folders.

3. DATABASE & FIREBASE INTEGRATION DEEP DIVE
================================================================================

Q: How is Cloud Firestore structured in PocketDay?
A: Firestore uses a UID-isolated subcollection hierarchy:
   users/ (Collection)
     └── {uid} (Document)
           ├── displayName, email, photoUrl, createdAt
           ├── transactions/ (Subcollection) -> TransactionModel documents
           ├── budgets/ (Subcollection) -> BudgetModel documents (month: YYYY-MM)
           ├── goals/ (Subcollection) -> GoalModel documents
           └── subscriptions/ (Subcollection) -> SubscriptionModel documents

Q: How does offline mode work in Cloud Firestore?
A: In main.dart, offline persistence is explicitly enabled:
   FirebaseFirestore.instance.settings = Settings(
     persistenceEnabled: true,
     cacheSizeBytes: Settings.CACHE_SIZE_UNLIMITED,
   );
   All read and write operations execute instantly (<5ms) against the local disk cache. 
   When the device reconnects to the internet, Firestore automatically synchronizes 
   queued writes with Google Cloud servers.

Q: How does PocketDay prevent security/privacy breaches between users?
A: Data is strictly isolated under `users/{uid}/*` subcollections. Firestore 
   Security Rules verify that `request.auth.uid == userId`, ensuring a user can 
   only read or write their own documents.

Q: How does PocketDay handle data reset without hitting Firestore limits?
A: Firestore limits batch operations to 500 writes. In `auth_repository.dart`, 
   the `resetAppData()` method deletes financial subcollections in chunked 
   400-document batches to avoid exceeding safety thresholds.

4. STATE MANAGEMENT & PERFORMANCE OPTIMIZATIONS
================================================================================

Q: Why was Riverpod chosen over Provider or Bloc?
A: 1. Compile-Time Safety: Riverpod does not depend on the BuildContext tree to 
      read state, preventing ProviderNotFoundException runtime crashes.
2. Immutability: StateNotifiers enforce unidirectional data flow.
3. Testability: Repositories and providers can easily be mocked for unit testing.

Q: How does the navigation shell prevent startup performance bottlenecks?
A: `AppMainNavigationScreen` uses a Lazy `IndexedStack` pattern (`_visitedIndices`). 
   On application startup, only Tab 0 (DashboardScreen) is instantiated. Tabs 1-4 
   return `SizedBox.shrink()` until the user taps them for the first time. Once tapped, 
   screens remain in memory so scroll positions and inputs are preserved.

Q: What is the difference between ref.watch() and ref.read()?
A: - `ref.watch()`: Listens to provider state changes and triggers a UI rebuild 
     whenever state changes (used inside `build()` methods).
   - `ref.read()`: Reads provider state or invokes notifier methods once without 
     subscribing to rebuilds (used inside event callbacks like button `onPressed`).

5. CORE WORKFLOWS & EXECUTION STEPS
================================================================================

WORKFLOW 1: Adding an Expense Transaction
1. User taps "+ Expense" -> opens `AddTransactionBottomSheet`.
2. Form validates input -> calls `ref.read(transactionsProvider.notifier).addTransaction()`.
3. Instantiates `TransactionModel` with UUID and type `TransactionType.expense`.
4. `TransactionRepository.addTransaction()` writes document to `users/{uid}/transactions/{id}`.
5. Firestore disk cache updates instantly -> emits stream update.
6. `transactionsProvider` updates state -> `dashboardProvider` recalculates metrics.
7. UI components (`DashboardCardWidget`, `SpendingChartWidget`) rebuild automatically.

WORKFLOW 2: Goal Progress Derivation
- Goals do not store a hardcoded current balance.
- `goalsProvider` watches `transactionsProvider`.
- `GoalCalculations.calculateCurrentAmount()` sums all income/expense transactions 
  where `txn.goalId == goal.id`.
- `GoalCard` renders real-time progress percentages dynamically.

WORKFLOW 3: Recurring Subscription Auto-Expense Recording
- `SubscriptionNotifier` runs `checkAndAutoRecordExpenses()` on load.
- Iterates over active subscriptions with `autoRecordExpense == true`.
- If `nextPaymentDate <= DateTime.now()`, creates a new expense transaction, 
  advances `nextPaymentDate` to the next billing cycle, and saves both to Firestore.

6. FINANCIAL FORMULAS IMPLEMENTED IN CODEBASE
================================================================================

1. Total Balance Formula (dashboard_provider.dart):
   Total Balance = Sum(Income Amounts) - Sum(Expense Amounts)

2. Safe Daily Spend Formula (dashboard_provider.dart):
   Days Left = Total Days in Current Month - Current Day + 1
   Safe Daily Spend = Max(0, Remaining Monthly Budget / Days Left)

3. Goal Progress Percentage (goal_model.dart):
   Current Amount = Sum(Transactions where goalId == goal.id)
   Progress % = Min(100, (Current Amount / Target Amount) * 100)

4. Subscription Monthly Equivalent (subscription_model.dart):
   Weekly    = Amount * (52 / 12)
   Monthly   = Amount
   Quarterly = Amount / 3
   Yearly    = Amount / 12

7. COMMON PRESENTATION VIVA QUESTIONS & WINNING ANSWERS
================================================================================

Q1: What happens if Firebase Firestore goes down or network is disconnected?
A: The application continues working seamlessly due to Firestore's native offline 
   cache engine. Users can add, edit, or delete transactions offline. All changes 
   are cached locally and automatically synced once connection returns.

Q2: Why is Goal balance calculated dynamically instead of stored as a field?
A: Calculating balance dynamically ensures Single Source of Truth (SSOT). If a user 
   deletes or edits a past transaction linked to a goal, the goal balance automatically 
   recalculates accurately without risking data desynchronization.

Q3: How does the app handle dark theme toggling?
A: `ThemeProvider` manages `ThemeMode` using Riverpod. `AppTheme` defines Material 3 
   light and dark `ThemeData`. Toggling the switch in ProfileScreen updates `ThemeNotifier`, 
   causing `MaterialApp` to rebuild with the new theme instantly.

Q4: What is unawaited async execution used for in AuthRepository?
A: When logging in, non-critical background tasks (like updating user profile metadata in 
   Firestore) are wrapped in `unawaited()`. This prevents the login UI from blocking or 
   hanging on poor network connections.

Q5: What unit tests are implemented in the project?
A: The `test/` directory contains unit test suites for:
   - `auth_session_test.dart`: Authentication state logic.
   - `budget_test.dart`: Monthly budget limit calculations.
   - `transactions_test.dart`: Income/expense balance math.
   - `goal_test.dart`: Target progress percentage math.
   - `subscription_test.dart`: Billing cycle renewal math.
